## ADDED Requirements

### Requirement: Authentication mode selection
The system SHALL support two pgwire authentication modes: `none`, where every connection is accepted without a password (the default), and `password`, where the client must complete a SCRAM-SHA-256 SASL exchange. The mode SHALL apply to every connection, whether it goes on to use the Simple or the Extended Query protocol.

#### Scenario: Default mode accepts any client
- **WHEN** no `[auth]` section is configured and a client connects without a password
- **THEN** the server completes startup with AuthenticationOk and the client can run queries

#### Scenario: Password mode advertises SCRAM-SHA-256
- **WHEN** `type = "password"` is configured and a client sends a StartupMessage
- **THEN** the server responds with AuthenticationSASL listing exactly `SCRAM-SHA-256`

### Requirement: SCRAM-SHA-256 verification
In password mode, the system SHALL verify the client proof against a stored PostgreSQL-format SCRAM-SHA-256 verifier (`SCRAM-SHA-256$<iterations>:<salt>$<StoredKey>:<ServerKey>`). The proof comparison SHALL be constant-time. On success, the server SHALL send SASLFinal with the server signature, followed by AuthenticationOk, ParameterStatus, BackendKeyData and ReadyForQuery. The user name is taken from the StartupMessage `user` parameter. The name inside the SCRAM message is ignored, as PostgreSQL does.

#### Scenario: Correct password
- **WHEN** a configured user connects with the correct password
- **THEN** authentication succeeds and both Simple and Extended Query statements run

#### Scenario: Verifier produced by another PostgreSQL implementation
- **WHEN** a user's `password_hash` is a verifier generated by a PostgreSQL-compatible tool
- **THEN** that user can authenticate with the matching password

### Requirement: Authentication failures are fatal
Any error during the authentication phase SHALL be reported with severity `FATAL`, and the connection SHALL be closed. A wrong password or an unknown user SHALL produce SQLSTATE `28P01` with the message `password authentication failed for user "<name>"`. An unknown user SHALL receive a salt that stays the same across attempts and looks like a real one, so probing cannot reveal which user names exist.

#### Scenario: Wrong password
- **WHEN** a configured user connects with an incorrect password
- **THEN** the server responds with ErrorResponse `FATAL 28P01` and closes the connection

#### Scenario: Unknown user
- **WHEN** a client connects as a user that is not configured
- **THEN** the server runs the SCRAM exchange with a decoy salt and responds with `FATAL 28P01`

#### Scenario: Query sent before authentication completes
- **WHEN** a client sends a Query message after receiving AuthenticationSASL instead of a SASLInitialResponse
- **THEN** the server responds with a FATAL ErrorResponse, returns no row data, and closes the connection

#### Scenario: Channel binding requested
- **WHEN** a client's SCRAM gs2 header requests channel binding (`p=...`)
- **THEN** the server rejects the exchange with a FATAL protocol-violation error
